在 Cesium Sandcastle 或自己的 Cesium 页面运行这些实验。每次只观察一层：Entity 状态、Visualizer 同步、Scene 帧事件、DrawCommand，最后把现象和源码对应起来。

准备：只创建一个红点

const viewer = new Cesium.Viewer("cesiumContainer", {
  requestRenderMode: true,
  maximumRenderTimeChange: Infinity
});

const pointEntity = viewer.entities.add({
  id: "beijing-point",
  position: Cesium.Cartesian3.fromDegrees(116.39, 39.9, 1000),
  point: {
    pixelSize: 14,
    color: Cesium.Color.RED,
    outlineColor: Cesium.Color.WHITE,
    outlineWidth: 2
  }
});

viewer.zoomTo(pointEntity);

先预测：`viewer.entities.add()` 返回时，GPU 是否已经执行 draw call？答案是否定的。这一行完成的是 EntityCollection 状态变更，转换和绘制发生在后续更新与渲染阶段。

实验 1：记录一帧的先后顺序

在创建 Viewer 后、添加 Entity 前运行下面代码。包装 `DataSourceDisplay.update` 只用于学习和调试，不应放进生产代码。

const display = viewer.dataSourceDisplay;
const originalUpdate = display.update.bind(display);

display.update = function (time) {
  console.log("1 DataSourceDisplay.update", Cesium.JulianDate.toIso8601(time));
  return originalUpdate(time);
};

viewer.scene.preUpdate.addEventListener(() => console.log("2 Scene.preUpdate"));
viewer.scene.preRender.addEventListener(() => console.log("3 Scene.preRender"));
viewer.scene.postRender.addEventListener(() => console.log("4 Scene.postRender"));

观察：默认循环里 `clock.tick()` 先触发 CesiumWidget 的 onTick 更新 DataSourceDisplay，然后 `Scene.render()` 才触发 Scene 的 preUpdate、preRender 和 postRender。日志证明状态同步和画面提交不是同一层。

验收：你能解释为什么文章不能写成 `Scene.render -> initializeFrame -> DataSourceDisplay.update`。

实验 2：截获这个点的 DrawCommand

`debugCommandFilter` 是 Scene 提供的调试入口。它在命令执行前被调用，返回 false 会阻止该命令执行。

let printed = false;

viewer.scene.debugCommandFilter = function (command) {
  const ownerName = command.owner?.constructor?.name;
  if (!printed && ownerName === "PointPrimitiveCollection") {
    printed = true;
    console.table({
      owner: ownerName,
      primitiveType: command.primitiveType,
      pass: command.pass,
      hasVertexArray: Boolean(command.vertexArray),
      hasShaderProgram: Boolean(command.shaderProgram),
      hasRenderState: Boolean(command.renderState),
      hasBoundingVolume: Boolean(command.boundingVolume)
    });
    console.log("Point DrawCommand", command);
  }
  return true;
};

viewer.scene.requestRender();

观察：PointPrimitiveCollection 生成的命令包含 vertexArray、shaderProgram、uniformMap、renderState、pass 和 boundingVolume。它的 `primitiveType` 是 POINTS，之后由 `DrawCommand.execute()` 交给 `Context.draw()`。

继续破坏：把匹配分支中的 `return true` 改成 `return false`。Entity 仍在 Collection 中，PointPrimitive 也可能存在，但红点消失，因为命令在 GPU 执行前被过滤。

实验 3：理解 requestRenderMode

// 修改业务状态
pointEntity.point.pixelSize = 28;

// 明确请求下一帧；异步资源或属性事件也可能自动请求渲染
viewer.scene.requestRender();

在按需渲染模式下，浏览器的 requestAnimationFrame 循环可以继续运行，但 Cesium 不必每次都提交新画面。`Scene.render()` 会综合 `_renderRequested`、相机变化、时间变化和资源状态判断是否真正渲染。

验收：能区分“浏览器帧循环还在运行”“Scene 正在更新状态”和“本次产生了新 framebuffer”三个概念。

自测

为什么 Entity 不能直接调用 gl.drawArrays？

Entity 描述位置、时间属性和业务图形；WebGL 需要确定的顶点缓冲、shader、uniform、渲染状态和图元类型。Visualizer、Primitive 和 DrawCommand 负责把前者逐步编译成后者。

PointVisualizer 和 PointPrimitiveCollection 各负责什么？

PointVisualizer 读取 Entity 在当前时间的属性并同步到 PointPrimitive；PointPrimitiveCollection 把一组点整理进 GPU buffer，准备 shader 和 render state，并向 frameState.commandList 提交 DrawCommand。

DrawCommand 已进入 commandList，为什么仍可能没有像素？

命令可能被视锥、遮挡或 debugCommandFilter 排除；也可能在执行后因深度测试、透明混合、裁剪区域、shader discard 或错误 framebuffer 而不产生可见颜色。

gl.drawArrays 返回后，为什么还不能把它等同于屏幕已经显示？

draw call 提交 GPU 工作；GPU 还要执行着色、光栅化、深度和混合并写入 framebuffer，浏览器还要把 WebGL canvas 与 DOM 合成后呈现。
