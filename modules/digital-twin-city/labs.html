公交车状态实验：乱序、重复、过期与闭环

用一辆公交车做最小数字孪生。目标不是画移动点，而是保证现实对象与数字状态之间的关系可以解释、回放和纠错。

实验 1：定义对象而不是图形

{
  "id": "bus-42",
  "position": [116.40, 39.90],
  "speedKph": 32,
  "observedAt": "2026-09-14T08:00:04Z",
  "receivedAt": "2026-09-14T08:00:06Z",
  "source": "gps-gateway-3",
  "version": 1842
}

解释 `observedAt` 与 `receivedAt` 的差异。删除 id、时间或版本中的任一项，说明系统会失去什么能力。

实验 2：处理乱序和重复事件

current.version = 1842
arrives: version 1844 -> accept
arrives: version 1843 -> keep in history, do not overwrite current
arrives: version 1844 -> deduplicate
arrives: version 1845 -> accept

只按“最后收到”覆盖会让车辆倒退。写出接收、拒绝、去重和进入人工复核的规则。

实验 3：表达数据过期

设定 10 秒、30 秒、2 分钟三个阈值。让地图区分“正在移动”“可能延迟”“已经失联”，而不是把最后位置永久显示成实时真相。

验收：前端状态必须由数据新鲜度推导，不能只看 WebSocket 是否连接。

实验 4：完成行动闭环

overspeed event
  -> rule or agent proposes alert
  -> operator confirms
  -> ticket is created
  -> driver response returns
  -> ticket closes
  -> response becomes part of history

为每一步标出执行者、权限、可审计记录和失败补偿。Agent 可以提出建议，但高风险动作需要明确授权。

自测

三维模型为什么不等于数字孪生？

三维模型主要表达几何与外观；数字孪生还需要对象身份、持续状态、时间历史、现实同步和决策反馈。

事件日志与当前状态为什么都要保存？

当前状态支持快速查询，事件日志支持回放、审计、纠错和重新计算。

实时连接存在，数据就一定实时吗？

不一定。连接可能持续传输延迟、重复或上游停滞的数据，必须检查事件时间与新鲜度。
